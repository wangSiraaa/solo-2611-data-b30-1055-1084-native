# 组织变更后的层级预算分解与支出占额

纯 Python 3.11 + 标准库（`sqlite3`）实现，无第三方依赖。两个服务物理分离、
仅通过**已发布的不可变组织产品版本**衔接，解决部门迁移后旧预算与已承诺
支出在新旧上级同时占额的问题。所有金额均为整数分。

## 目录结构

```
orgbudget/
  errors.py          领域异常（组织错误与预算错误各自成体系）
  budget.py          纯函数分解：按权重大数余数法（下取整 + 余数降序 + ID 并列）
  org_service.py     组织编制服务：唯一根父子树、子树移动、叶停用、不可变版本快照
  budget_service.py  预算执行仓：根预算、权重分解、承诺、实际支出、换版与覆盖校验
  audit.py           独立重算审计（Fraction 独立实现 + 直接读原始事件表核对）
canteen/
  errors.py          餐签 / 场次 / 托管柜的领域异常
  model.py           纯数据：菜、锅、桌、场次、工单
  vouchers.py        餐签面额取实付 + 通用/限桌/限班点联合审批（含冲突最小见证）
  kitchen.py         余味 / 时隙 / 备料约束下的整场工单回溯排程
  runtime.py         按格依次执行、实扣、仅追加事件与交班保留
  ticketing.py       高峰两种经营方式：具名菜单联 / 共享托管柜
  session.py         审批 + 排程 + 执行串成可批准整体；高峰二选一入口
demo/
  scenarios.py       六个组织预算端到端案例
  canteen_scenarios.py  六个食堂端到端案例
tests/               64 个 unittest 用例（含跨进程争用、排程模糊校验、联合审批）
```

## 运行

```bash
python3 -m unittest discover -s tests -v   # 测试
python3 -m demo.scenarios                  # 组织预算端到端演示，产物落在 demo_data/*.db
python3 -m demo.canteen_scenarios          # 食堂端到端演示（用临时库，跑完即删）
```

## 核心规则与实现落点

### 组织编制服务（`OrgService`，独立 SQLite 库）

- 唯一 `department_id`、唯一根、父子树；建部门 / 移动完整子树 / 停用叶部门。
- 移动只改被移动节点一条父边：天然是整棵子树移动，不存在“部分移动”；
  根不可移动，挂到自身或子孙下报 `CycleError`，发布时 `OrgProduct` 构造器
  再做单根 / 无环 / 唯一父项全量校验。
- 每次 `publish()` 把全量快照写入 `org_dept`，版本号严格递增；
  **已发布产品不可变**，后续移动只产生新版本，旧版本行永不更新。
- 组织维护独立于预算，行政客户可直接用祖先 / 后代 / 子树查询。

### 预算执行仓（`BudgetService`，另一个独立 SQLite 库）

- 每个方案在 `scheme` 表明确绑定一个组织产品版本；预算端查询时按方案绑定
  的版本实时向组织服务读取**本次产品**，不缓存旧树，迁移部门不可能出现
  两份额度。
- 分解（`budget.allocate_children`）：按权重比例下取整，丢掉的分按小数余数
  降序补，余数并列按部门 ID 升序；恒有 `Σ孩子预算 = 父预算`。
- 叶可用额 = 分配预算 − 实际支出 − 未结承诺剩余，开立承诺时在事务内校验，
  不得为负；支出仅追加，不得超过承诺剩余；取消只释放剩余，已支出不可撤销。
- 承诺 `request_no` 是全局唯一幂等键，支出事件有独立幂等键，丢响应重试
  不二次占额；同键不同内容报 `IdempotencyConflict`。
- 换版 `revise_budget()`：预算人员为**新产品**的每条直接父子边补齐正权重
  （缺边 / 多边均拒绝），自根向下重算全部预算，再用全部历史承诺 / 支出
  事件做覆盖校验。任一叶覆盖不了“实际支出 + 未结承诺剩余”则整次换版
  回滚并在 `rejected_revision` 留痕；**承诺的部门身份永不改写**。
- 拒绝不影响组织服务已发布的新产品，预算仓继续绑定旧版。
- 汇总沿方案绑定产品的树闭包计算；旧方案查询永远沿旧树，不按当前树解释历史。

### 并发与持久化

- 所有写操作在单连接 `BEGIN IMMEDIATE` 事务内完成“读取校验 → 写入”，
  SQLite 写锁把并发提交串行化；测试覆盖线程与**独立进程**两种争用，
  两个连接争同一剩余额时最多一方成功。
- 全部状态落 SQLite 文件，服务重启后事实完整可读。

### 独立审计（`audit.audit_scheme`）

刻意不调用生产代码的分解 / 汇总路径：

1. 直接 SQL 读组织快照、承诺与仅追加支出事件；
2. 用 `fractions.Fraction` 重新推导分解，与落库分配逐部门比对；
3. 从原始事件重建每叶实际支出与未结占额，逐级核对守恒、覆盖、可用额非负、
   祖先汇总 = 后代叶事实之和。2000 组随机参数下两套实现结果完全一致；
   直接篡改分配或事件表会被审计抛出 `InvalidTree`。

## 演示案例（`python3 -m demo.scenarios`）

1. 三层树余分分配（含余数并列按 ID、不同余数两种情形，并与 Fraction 实现交叉核对）；
2. 带未结承诺的部门子树迁移、换版重算、身份不改、旧版沿旧树冻结；
3. 新预算不足被整次拒绝，组织新产品照发，预算仓继续绑旧版；
4. 支出后部分取消：已支出保留、剩余占额释放、取消后禁止再支出；
5. 并发承诺争额度最多一方成功、同请求重试不二次占额（线程级）；
6. 20 部门 / 深度 5 / 100 笔支出的大规模场景，迁移前后各做一次独立审计。

## 食堂演示案例（`python3 -m demo.canteen_scenarios`）

1. 面额取实付：承诺 5、实付 3 只印 3 点；零实付拒印；取消后已付仍可印；
2. 两桌白汤，一口初始干净的锅连做，无需洗锅；
3. 实付 5 只够连做两白、白原料只剩一份时原料不足；实付 4（第五点停在承诺）
   无法支付两白（需 5 点），上午只能点蓝；
4. 菜单一起付得起（AM 蓝 + NOON 白 = 4 点）却来不及洗锅；放开 NOON 槽位后
   “蓝、洗、白”复活；
5. 两桌分开各自够、合起来却同花一张限班点：联合审批给出最小见证；
6. 高峰二选一：两张满额联超全场保留额被拒；共享托管柜把唯一加价号发给开柜后
   才发现的缺货桌，卡掉发号窗口则判定无法保证两桌都吃上。

## 食堂：餐签、后厨排程与高峰经营方式（`canteen`）

建立在 `orgbudget` 的**实付事实**之上，点即整数赞助点；“余味 / 前味”用
展会虚构颜色表示（`clean` 为洗净空锅）。

### 餐签与点数（`canteen.vouchers`）

- **面额取实际付款**：`issue_voucher` 的面额 = 该赞助原件在预算仓已实际支出
  的累计金额；只承诺、未实付的原件（`spent == 0`）直接拒印。取消承诺只释放
  未花剩余，已付部分照旧可印。
- **加餐基金限同预算分部**：`Voucher.top_up` 的签仅当 `voucher.division` 与
  场次分部相同时可用。
- **联合审批**：多桌菜单一起批被建模为「签 → 桌」二部容量流；通用 / 限桌 /
  限班点可共同支付，同一张签的点至多被一桌消耗一次。额度不足时按 Hall 条件
  枚举桌的子集，给出**最小冲突桌集**——精确识别"两桌分开各自够、合起来却同
  花同一张限班点"。

### 后厨排程（`canteen.kitchen`）

- 每口锅每格只做一份或洗锅；做完菜余味改为该菜 `residual`，洗锅清成 `clean`。
- 一份菜仅在当前余味 ∈ `allowed_prev` 时可下锅；一桌的餐按一格，须落在其
  `acceptable_slots`。
- 备料整场共用，实际耗用不得超过 `stock`。回溯搜索按“格 → 锅 → 桌/洗/闲”，
  以“剩余桌仍有时隙 / 容量”剪枝；找不到即抛 `OrderNotFulfillable`，原料总量
  不足先抛 `StockShortfall`。

### 执行与交班（`canteen.runtime`）

- 按工单依次执行，端出的实菜、耗用原料、扣除点数全部写成**仅追加**事实；
  每桌至多一份、点数须与批准逐点对账。
- `handover()` 生成不可回滚的交班快照；`ShiftBook` 汇总跨班事实，并让下一班
  知道哪些桌已端出、不能以新菜单覆盖。
- `free_trial=True` 的普通对照试做照常排程执行，但不落任何扣点事件。

### 高峰二选一（`canteen.ticketing` / `canteen.session`）

- **具名菜单联**：开场给每桌封联，按最高可扣额保留；未下锅的联可退回、释放
  保留额后改给另一桌。`ReservationLedger` 同时守住每桌上限与全场总上限——两张
  各提 1 点的联会让保留额 2 超过全场 1 点，第二种封联直接被拒。
- **共享托管柜**：共享点数托管后厨同一个柜；掌厨在知道本班原料到货/缺货后、
  下锅前请求一个具名扣点号，**每拍只能发一个**。开柜后才发现缺货桌时，唯一
  加价号可发给它；若把“知道缺货”与“下锅”之间唯一可发号的拍也卡掉，则判定
  无法保证两桌都吃上（`plan_peak_shared_cabinet` 返回不可行并说明原因）。
